MaDI-Bench: An End-to-End Data Integration Benchmark

Aaron Steiner, Ralph Peeters, Christian Bizer
Data and Web Science Group, University of Mannheim
Paper Code & Data PyDI

Abstract

Data integration combines heterogeneous data from multiple sources into a single, coherent data set. Data integration involves a sequence of interdependent tasks: schema matching, value normalization, entity blocking, entity matching, and data fusion. Existing data integration benchmarks either evaluate these steps in isolation or cover only incomplete versions of the data integration pipeline, omitting specific steps. The lack of public end-to-end data integration benchmarks hinders research on data integration methods that address the integration process as a whole.

The Mannheim Data Integration Benchmark (MaDI-Bench) fills this gap. MaDI-Bench is the first benchmark for the end-to-end integration of relational tables covering all steps of the integration process. MaDI-Bench contributes (i) a set of base end-to-end data integration tasks spanning several application domains, each requiring the full schema matching, value normalization, entity matching, and conflict resolution pipeline; and (ii) a generic method for deriving variants of the base tasks that mitigates the rapid saturation of the benchmark as data integration systems advance. We validate MaDI-Bench using human-engineered pipelines, a best-of-breed pipeline, and an LLM-based pipeline. The validation demonstrates the utility of the benchmark for measuring the step-wise as well as the end-to-end performance of data integration pipelines. All benchmark artefacts are available for public download.

The Base Tasks

MaDI-Bench consists of five end-to-end data integration tasks. These base task require the integration of data about Games, Companies, Music, Products, and Scientific Papers. Each task takes several heterogeneous tables as input and asks the system under test (SUT) to integrate these tables into a single output table conforming to a given target schema. The integration requires the SUT to perform schema matching, value normalization, entity matching, and data fusion. The benchmark provides ground truth to score every step on its own, not only the final table: a gold schema mapping for schema matching, the target schema's constraints and taxonomies for value normalization (measured as consistency with the schema), labeled record pairs for blocking and entity matching, and hand-verified records for data fusion, together with metrics for the end-to-end result. MaDI-Bench offers easy, medium, and hard variants of each base task.

Artifacts per Task

MaDI-Bench provides the following artifacts for each of the base tasks:

  • Source tables and table metadata. One table per source, each with a metadata file recording its origin, the columns it contains, and the date it was published. Example: forbes.csv, forbes_metadata.json
  • Target schema. The columns of the fused table, with a value constraint per attribute (for example a valid founding-year range) and categorical attributes tied to standard taxonomies such as GICS industries and CLDR country names. Example: target_schema.json
  • Gold schema mapping. A correspondence from every source column to the target schema. Example: sm_mapping_gold.json
  • Entity matching sets. Labeled train, validation, and test pairs for each pair of sources. Example: forbes_2_dbpedia_train.csv
  • Fusion validation and test sets. 100 validation and 100 test entities per task, hand-annotated with the verified value for every attribute. Example: validation_set.xml
  • Reference outputs. The output of the human-engineered pipeline, used as a silver standard. Example: companies/base/output/

The sources describe the same kind of entity but rarely agree on column names, value formats, or even the facts themselves, which is what makes the merge hard.

The Integration Pipeline

A system under test (SUT) needs to handle the following four steps of the overall integration task. MaDI-Bench provides ground truth or a reference signal for each step as well as for the output of the overall integration (fused dataset). Thus, a SUT can be evaluated one step at a time or in an end-to-end fashion.

1Schema Matching

Sources rarely share column names, so every source column has to be matched to a column in the target schema before values can be combined. Names may be descriptive, abbreviated, or meaningless, and where a name gives nothing away, a matcher has to read the values instead.

Ground truth: gold schema mappingMetric: F1 over column correspondences

Example  ·  company, org_name and Attribute_2 all map to name
forbes · company → name
dbpedia · established → founded
dbpedia · headquarters → city
fullcontact · Attribute_2 from values only → name
fullcontact · Attribute_6 from values only → founded

2Value Normalization

Matched columns still store values in different formats and vocabularies, so they are rewritten into the forms the target schema requires. The schema sets a constraint for every attribute: a data type, and where it applies a numeric range, a string pattern, or a date format. A founding date, for instance, must be an ISO YYYY-MM-DD inside an allowed range, and assets must be a non-negative integer in US dollars below an upper bound. For categorical attributes, the task provides taxonomies that specify which values are allowed and how detailed the normalized values should be. Some attributes use standard taxonomies, e.g. countries follow CLDR, industries uses GICS. In addition, some tasks also use propretary taxonomies, for instance for platform, genre, and rating in the Games task. Normalization is scored as consistency, that is, whether the output values satisfy the given schema constraints.

3Entity Blocking & Matching

The SUT must identify records referring to the same real-world entity across sources. Since comparing all record pairs requires scoring the full Cartesian product and is therefore quadratic in the input size, this quickly becomes computationally infeasible. Blocking addresses this issue by reducing the search space to a smaller set of candidate pairs, after which matching classifies each candidate as either a match or a non-match. The MaDI-Bench entity matching test sets are designed to contain a decent amount of hard-to-decide corner case record pairs.

Ground truth: labeled pairsMetric: pair completeness & reduction ratio (blocking), F1 (matching)

4Data Fusion

After matching, records referring to the same real-world entities form clusters. Data fusion consolidates these clusters into a single record per cluster. When records provide conflicting values, the SUT must apply a conflict resolution heuristic to decide which value to retain. The values in the MaDI-Bench data fusion test sets are verified by humans who checked them against data from relevant websites.

Ground truth: hand-verified fused recordsMetric: fusion accuracy

End-to-End Evaluation

Beyond the per-step evaluation, MaDI-Bench also provides code for assessing the final output table along three quality dimensions: coverage (did the right entities and values make it into the output table?), consistency (does the table fit the target schema?), and correctness (are the fused values correct?). MaDi-Bench provides for assessing these quality dimension using different types of reference data: reference-free (no ground truth used, only structural comparison to imput), silver (comparison to the output of the human-designed pipelines), and ground truth (evaluation against the human-verified test sets). While the silver evaluation checks all values of the output table, the round truth-based evaluation covers only a subset of all records.

Validation

We validate MaDI-Bench using three pipelines that span the design space from human-engineered to fully automated. The human-engineered and LLM-based pipelines build on the PyDI integration framework, while the best-of-breed pipeline chains specialized systems from the literature. The per-step and end-to-end outputs of all three pipelines are found in the repository under results/ and the per-task output/ folders.

P1Human-engineered Pipelinessilver reference

The humain-engineered pipelines are task workflows that were coded by master's and PhD students using the PyDI framework. The students improved their workflows over multiple iterations using the MaDi-Bench validation sets. Every workflow involves the same sequence of steps: PyDI's LLM schema matcher proposes attribute correspondences between the input tables, an human data engineer inspects and hand-corrects the mapping, and the input tables are translated into the target schema. A normalization step then parses dates and numbers, converts units, and applies the taxonomy mappings. Blocking uses embedding or task-specific blocking keys tuned to reach at least 97% pair completeness. Entity matching combines rule-based or trained tree-based matchers with a global one-to-one correspondence creation step. Data fusion applies per-attribute conclict resolution heuristics such as source trust, longest or shortest string, numeric aggregation, and set union. The heuristics were selected by the students from the set of fusion heuristics offered by PyDI.

The human-engineered pipelines set a practical reference point on how data engineers would approach the MaDI integration tasks. The pipelines are likely not the optimum. In order to compare the performance of SUTs to human data-engineering, we use output of the human-engineered pipelines as silver standard.

Code and outputs: PyDI framework · workflow notebook · silver outputs

P2Best-of-breed Pipelinecommittee per step

The best-of-breed pipeline chains methods from the literature into an integration pipeline. For each step of the integration process, the method runs a committee of competing methods and scores their results on the validation sets. The winning method is selected for the best-of-breed pipeline and the winner's output is passed to the next stage of the process. Below, we list the methods that are tested for the different steps of each integration task:

Schema matching: COMA, Magneto, a Sentence-BERT embedding matcher, and PyDI's label-, instance-, duplicate- and LLM-based matchers. Blocking: standard, token and sorted-neighborhood blocking, BM25, Sentence-BERT, and SC-Block, keeping the blocker that clears 97% pair completeness at the highest reduction ratio. Entity matching: Ditto and Magellan. Fusion: PyDI heuristics plus the TruthFinder, LTM, AccuSim, CASEFusion, and FusionQuery truth-discovery models, with a per-attribute selector.

Outputs: results/best of breeds · per-stage method selections for one run

P3LLM-based Pipelineautomatic, self-configuring

The LLM-based pipeline uses an LLM to configure a end-to-end data integration pipeline which employs scalable, traditional integration methods for each step of the pipeline. The LLM-based pipeline uses the same PyDI methods as the human pipeline, but an LLM, not a human, configures them. GPT-5.5 performs schema matching, and the values are normalized by mapping them to the predefined taxonomies, with a column profiler selecting a normalization function for the remaining attributes. An embedding blocker then generates candidate pairs. Using a subset of those pairs, the pipeline generates its own machine-labeled training and validation sets using GPT-5.2 as the labeler. Thus, the pipeline uses training and validation sets that differ from the sets provided by the benchmark. The pipeline uses the machine-labeled sets to train and validate different similarity feature-based matchers using random forests and XGBoost. For fusion it writes a configuration that assigns each attribute a conflict-resolution heuristic. The LLM only configures the pipeline and generates the training artifacts; it is not involved in the integration itself, which keeps costs low and enables the pipeline to scale to large tasks.

Variant Generation

To keep the benchmark hard as systems improve, each base task also ships in easy, medium, and hard versions. The underlying entities and their true matches stay the same. Eight difficulty knobs perturb the data, each set to its own target for easy, medium, and hard. A harder level turns up the kinds of heterogeneity that real integration runs into.

Difficulty Knobs

Each knob targets one or two pipeline stages and is set to an easy, medium, or hard target. MaDI-Bench uses eight:

Knob 1 Matching · Fusion

Surface augmentation

Rewrites attribute values into other surface forms using abbreviations, token reorderings, and dropped tokens. This erodes the surface overlap that blocking and matching depend on, and turns clean values into plausible-looking disagreements for fusion.

exampleSan Francisco → Francisco San

Knob 2 Blocking · Matching

Entity niche density

Adds similar-but-distinct entities within the same domain niche, such as many products from one brand. Blocks fill up with non-matching pairs, and more candidate pairs sit close to the match / non-match boundary.

examplegenerates a near-duplicate company and inserts it into a crowded niche

Knob 3 Blocking · Matching · Fusion

Attribute drop

Blanks a share of cells per source. Missing blocking keys make records unreachable, missing attributes weaken the evidence for matching, and sparse coverage leaves fusion less to cross-check.

examplerevenue 358,500,000 → (dropped)

Knob 4 Matching · Fusion

Coverage skew

Varies how many sources describe each entity. This changes cluster sizes and thins the evidence available to resolve conflicts for entities that only one or two sources cover.

exampleInter RAO: its DBpedia row is removed, leaving fewer sources

Knob 5 Normalization

Format & unit diversity

Rewrites dates, numbers, and quantities into more formats, units, and scales, for example ISO against dotted dates, or raw figures against millions. More admissible forms per field make value standardization harder.

example65,170,000,000 → 65170 (millions)

Knob 6 Normalization · Matching · Fusion

Value noise

Corrupts a share of values with typos, encoding artifacts, and truncation. The damaged values lower string-similarity scores during matching and show up as spurious disagreements during fusion.

example2005-01-01 → 2o0t-01-o1

Knob 7 Schema matching

Schema naming divergence

Renames source columns along a scale from fully descriptive, through abbreviated, to opaque codes. At the hard end the column name carries no signal, so a matcher has to rely on the values alone.

exampletotal_assets_val → ta

Knob 8 Fusion

Source reliability

Reshuffles which source holds the correct value per attribute, so the most reliable source is right for only a share of entities. No fixed source-trust rule stays optimal.

exampleAccor: the verified name is reassigned to a different source

Two further knobs (value ambiguity and schema distractors) are specified for synthetic tasks. Full specifications for every knob are in the repository.

Conclusion

This paper introduced the MaDI-Bench integration benchmark. The benchmark models the full complexity of the data integration process, including schema matching, value normalization, entity matching, and conflict resolution, while at the same time taking into account the dependencies between the subtasks. To prevent a quick saturation of the benchmark as agentic systems progress, we introduce a generic variant-generation method for deriving harder variants from the base tasks. We validated MaDI-Bench and the generated variants using human-designed pipelines, an LLM-based pipeline, and a best-of-breed pipeline. The validation showed the benchmark's utility for measuring the step-wise as well as end-to-end performance of data integration systems. We hope that the benchmark will prove useful for the community and will support the development of fully automatic as well as human-in-the-loop data integration systems.
