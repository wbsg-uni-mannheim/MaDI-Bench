MaDI-Bench: An End-to-End Data Integration Benchmark

Aaron Steiner, Ralph Peeters, Christian Bizer
Data and Web Science Group, University of Mannheim
Paper Code & Data PyDI

Abstract

Data integration is the process of combining data from multiple, heterogeneous sources into a consistent, unified representation. Data integration involves a sequence of interdependent tasks including schema matching, value normalization, blocking, entity matching, and data fusion. Existing table-based benchmarks either evaluate these steps in isolation or cover only incomplete versions of the data integration pipeline, omitting specific steps. The lack of public end-to-end data integration benchmarks hinders research on data integration methods that address the integration process as a whole and account for the interdependencies among the different tasks.

This paper fills this gap by introducing the Mannheim Data Integration Benchmark (MaDI-Bench), the first benchmark for the end-to-end integration of relational tables covering all steps of the integration process. MaDI-Bench contributes (i) a set of end-to-end data integration tasks spanning several application domains, each requiring the full schema matching, value normalization, entity matching, and data fusion pipeline, and (ii) a generic method for deriving task variants that mitigates rapid benchmark saturation as data integration systems advance. We validate the benchmark using human-engineered pipelines, a best-of-breed pipeline, an LLM workflow, and a pipeline written by a coding agent. The validation demonstrates the utility of the benchmark for measuring the step-wise as well as the end-to-end performance of data integration pipelines. All benchmark artifacts are available for public download.

The Base Tasks

MaDI-Bench consists of five base end-to-end data integration tasks. These base tasks require the integration of data about Games, Companies, Music, Products, and Scientific Papers. Each task takes several heterogeneous tables as input and asks the system under test (SUT) to integrate these tables into a single output table conforming to a given target schema. The integration requires the SUT to perform schema matching, value normalization, blocking, entity matching, and data fusion. The benchmark provides ground truth to score every step on its own, not only the final table: a gold schema mapping for schema matching, labeled normalization sets for value normalization, labeled record pairs for blocking and entity matching, and human-verified records for data fusion, together with metrics for the end-to-end result. MaDI-Bench offers an easy, a medium, and a hard variant of each base task, 20 tasks in total.

Artifacts per Task

MaDI-Bench provides the following artifacts for each of the base tasks:

  • Source tables and table metadata. One table per source, each with a metadata file recording its origin, the columns it contains, and the date it was published. Example: forbes.csv, forbes_metadata.json
  • Target schema. The columns of the fused table, with a value constraint per attribute (for example a valid founding-year range) and categorical attributes tied to standard taxonomies such as GICS industries and CLDR country names. Example: target_schema.json
  • Gold schema mapping. The correspondences from the source columns to the attributes of the target schema. Example: sm_mapping_gold.json
  • Normalization sets. A validation and a test set of source cells, each paired with its correctly normalized value; 1,745 cells across the five base tasks. Most cells need a formatting rule or a mapping onto a vocabulary that the task provides; some already hold the correct value and test that a normalizer leaves it intact. Example: test.csv
  • Entity matching sets. Labeled train, validation, and test pairs for two pairs of sources per task (three for Products); more than 93,000 pairs across the five base tasks. The test pairs also evaluate blocking. Example: forbes_2_dbpedia_train.csv
  • Fusion validation and test sets. 100 validation and 100 test entities per task with human-verified attribute values; close to 8,000 values across the five base tasks. All tasks use version 2 of the fusion gold, which leaves out the values that cannot be obtained from any source record of the entity, even after normalization. Example: validation_set.xml
  • Reference outputs. The output of the human-engineered pipeline (P1), whose clusters with at least two source records form the silver reference for the end-to-end metrics. Example: companies/base/output/

The easy, medium, and hard variants come with their own source tables, gold schema mapping, and entity matching and normalization sets. They keep the fusion entities and gold values of their base task.

The sources describe the same kind of entity but rarely agree on column names, value formats, or even the facts themselves, which is what makes the merge hard.

The Integration Pipeline

A system under test (SUT) needs to handle the following steps of the overall integration task. MaDI-Bench provides ground truth for each step as well as for the output of the overall integration (fused dataset). Thus, a SUT can be evaluated one step at a time or in an end-to-end fashion.

1Schema Matching

Sources rarely share column names, so the source columns have to be matched to the attributes of the target schema before values can be combined. Source columns without a matching target attribute stay unmapped. Names may be descriptive, abbreviated, or meaningless, and where a name gives nothing away, a matcher has to read the values instead.

Ground truth: gold schema mappingMetric: F1 over column correspondences

Example  ·  company, org_name and Attribute_2 all map to name
forbes · company → name
dbpedia · established → founded
dbpedia · headquarters → city
fullcontact · Attribute_2 from values only → name
fullcontact · Attribute_6 from values only → founded

2Value Normalization

Matched columns still store values in different formats and vocabularies, so they are rewritten into the forms the target schema requires. The schema sets a constraint for every attribute: a data type, and where it applies a numeric range, a string pattern, or a date format. A founding date, for instance, must be an ISO YYYY-MM-DD inside an allowed range, and assets must be a non-negative integer in US dollars below an upper bound. For categorical attributes, the task provides taxonomies that specify which values are allowed and how detailed the normalized values should be. The taxonomies ship with the task: some follow a standard, for example CLDR for countries and GICS for industries; others cover domain vocabularies such as the platforms, genres, and ESRB ratings of the Games task. Normalization is scored as accuracy on the normalization test set: each test cell pairs a source value with its correctly normalized value. The test cells include values that are already correct, so a normalizer that changes correct values loses accuracy.

3Entity Blocking & Matching

The SUT must identify records referring to the same real-world entity across sources. Since comparing all record pairs requires scoring the full Cartesian product and is therefore quadratic in the input size, this quickly becomes computationally infeasible. Blocking addresses this issue by reducing the search space to a smaller set of candidate pairs, after which matching classifies each candidate as either a match or a non-match. The MaDI-Bench entity matching test sets are designed to contain many hard-to-decide corner-case record pairs.

Ground truth: labeled pairsMetric: pair completeness & reduction ratio (blocking), F1 (matching)

4Data Fusion

After matching, records referring to the same real-world entities form clusters. Data fusion consolidates these clusters into a single record per cluster. When records provide conflicting values, the SUT must resolve the conflict and decide which value to retain, for example with a conflict resolution heuristic or a learned truth-discovery model. The values in the MaDI-Bench data fusion test sets are verified by humans who checked them against data from relevant websites.

Ground truth: hand-verified fused recordsMetric: fusion accuracy (share of verified cells with a correct value)

End-to-End Evaluation

Beyond the per-step evaluation, MaDI-Bench assesses the final output table along three quality dimensions: coverage (did the right entities and values make it into the output table?), consistency (does the table fit the target schema?), and correctness (are the fused values correct?). The metrics use three types of reference data: reference-free (no ground truth, structural and schema checks of the output, some of them relative to the input tables), silver (comparison with the clusters of the human-engineered pipeline P1 that combine at least two source records), and ground truth (comparison with the human-verified fusion test sets). The silver reference covers a much larger part of the output table, while the ground truth covers only the test entities but gives the stronger guarantee of correctness.

Validation

We validate MaDI-Bench using four pipelines that span the design space from human-engineered to fully LLM-driven. The human-engineered pipelines (P1) and the LLM workflow (P3) build on the PyDI integration framework. The best-of-breed pipeline (P2) chooses, for each step, between specialized methods from the literature and methods of PyDI. The coding agent Claude Code (P4) writes and runs its own integration code without PyDI.

P1Human-engineered Pipelinessilver reference

The human-engineered pipelines are task workflows that were coded by master's and PhD students using the PyDI framework. The students improved their workflows over multiple iterations using the MaDI-Bench validation sets. Every workflow involves the same sequence of steps: PyDI's LLM schema matcher with GPT-5 proposes attribute correspondences between the input tables, a human data engineer inspects and hand-corrects the mapping, and the input tables are translated into the target schema. A normalization step then parses dates and numbers, converts units, and applies the taxonomy mappings. Blocking uses embedding or task-specific blocking keys tuned to reach at least 97% pair completeness. Entity matching uses rule-based or trained tree-based matchers, followed by a global one-to-one matching step where the engineers found it necessary. Data fusion applies per-attribute conflict resolution heuristics such as voting, source trust, longest or shortest string, numeric aggregation, and set union. The heuristics were selected by the students from the set of fusion heuristics offered by PyDI.

The human-engineered pipelines set a practical reference point on how data engineers would approach the MaDI-Bench integration tasks. The pipelines are likely not the optimum. In order to compare the performance of SUTs to human data engineering, we use the output of the human-engineered pipelines as the silver standard.

Code and outputs: PyDI framework · workflow notebook · silver outputs

P2Best-of-breed Pipelinecommittee per step

The best-of-breed pipeline chains methods from the literature and from PyDI into an integration pipeline. For each step of the integration process, the pipeline runs a committee of competing methods and scores their results on the validation sets. The winning method is selected for the best-of-breed pipeline and the winner's output is passed to the next step of the process. Below, we list the methods that are tested for the different steps of each integration task:

Schema matching: COMA, Magneto, a Sentence-BERT embedding matcher, and PyDI's label-, instance-, duplicate- and LLM-based matchers (GPT-5.4-mini). Normalization: the source values left unchanged, or a rule-based normalizer that applies a type-specific rule per attribute (text cleaning, date parsing, locale-aware number parsing, country-code or taxonomy lookup). Blocking: standard, token and sorted-neighborhood blocking, BM25, Sentence-BERT, and SC-Block, keeping for each pair of sources the blocker with the highest reduction ratio among those that reach 97% pair completeness on the validation set. Blockers with more than five million candidate pairs are excluded. If no blocker reaches 97%, the one with the highest pair completeness is kept. Entity matching: Ditto and Magellan. Fusion: PyDI heuristics with a per-attribute selector that keeps the heuristic with the best validation score for each attribute, plus the TruthFinder, LTM, AccuSim, CASEFusion, and FusionQuery truth-discovery models.

Code: pipelines · Outputs: results/best of breeds · per-stage method selections for one run

P3LLM Workflowautomatic, self-configuring

The LLM workflow uses an LLM to configure an end-to-end data integration pipeline that employs scalable, traditional integration methods for each step. It uses the same PyDI methods as the human-engineered pipelines, but an LLM, not a human, configures them. GPT-5.5 performs schema matching, taxonomy mapping, and the fusion configuration, and the values are normalized by mapping them to the predefined taxonomies, with a column profiler selecting a normalization function for the remaining attributes. An embedding blocker then generates candidate pairs. Using a sample of those pairs, the workflow generates its own machine-labeled training and validation sets, with GPT-5.2 as the labeler. These sets are independent of the sets that the benchmark provides. The workflow uses them to train and validate rule-based matchers and similarity feature-based models such as random forests and XGBoost. For fusion, the LLM assigns each attribute a conflict-resolution heuristic from PyDI. The workflow builds several such configurations, some of them tuned on the fusion validation set of the benchmark, and keeps the one with the highest accuracy on that set. Apart from schema matching and taxonomy mapping, the LLM configures the methods and generates the training data but does not integrate the records itself, which keeps costs low and lets the workflow scale to large tasks.

Code: baselines/llm-pipeline · Outputs: results/llm pipeline · a sample run

P4Claude Code Pipelinecoding agent, no labels

P4 uses the coding agent Claude Code 2.1.280 with Claude Opus 5.5 to write and execute its own integration pipeline for each task. The agent runs unsupervised in an isolated workspace. It receives the source tables with their metadata files, the target schema, the taxonomies, and a short description of what counts as an entity in the domain. It receives no labeled data, PyDI and its documentation are not available, and web search and web fetching are disabled. Instead, the agent receives seven skills written by the authors, for schema matching, normalization, blocking, entity matching, clustering, fusion, and pipeline diagnosis, which describe possible methods, typical errors, and checks for each step. An OpenAI embeddings endpoint is available; the agent used it only on the three Companies variants. The agent inspects the sources, writes code for every step, runs it, checks diagnostics such as missing values, schema conformity, and cluster sizes, and revises the code in the same run. Each run is limited to 18 hours of wall-clock time and 100 US dollars of LLM spend.

Variant Generation

To keep the benchmark hard as systems improve, each base task also ships in easy, medium, and hard versions. The knobs keep the identity of every retained record and its true matches. Two knobs add near-duplicate entities or remove records from some sources. Eight difficulty knobs perturb the data, each set to its own target for easy, medium, and hard. A harder level turns up the kinds of heterogeneity that real integration runs into, while the easy level supports the evaluation of simpler and cheaper methods. The easy level makes schema and entity matching easier, but not fusion.

Difficulty Knobs

Each knob targets one or more pipeline stages and is set to an easy, medium, or hard target. MaDI-Bench uses eight:

Knob 1 Blocking · Matching · Fusion

Surface augmentation

Rewrites attribute values into other surface forms using abbreviations, token reorderings, and dropped tokens. This erodes the surface overlap that blocking and matching depend on, and turns clean values into plausible-looking disagreements for fusion.

exampleSan Francisco → Francisco San

Knob 2 Blocking · Matching

Entity niche density

Adds similar-but-distinct entities within the same domain niche, such as many products from one brand. Blocks fill up with non-matching pairs, and more candidate pairs sit close to the match / non-match boundary.

examplegenerates a near-duplicate company and inserts it into a crowded niche

Knob 3 Blocking · Matching · Fusion

Attribute drop

Blanks a share of cells per source. Missing blocking keys make records unreachable, missing attributes weaken the evidence for matching, and sparse coverage leaves fusion less to cross-check.

examplerevenue 358,500,000 → (dropped)

Knob 4 Matching · Fusion

Coverage skew

Varies how many sources describe each entity. This changes cluster sizes and thins the evidence available to resolve conflicts for entities that only one or two sources cover.

exampleInter RAO: its DBpedia row is removed, leaving fewer sources

Knob 5 Normalization

Format & unit diversity

Rewrites dates, numbers, and quantities into more formats, units, and scales, for example ISO against dotted dates, or raw figures against millions. More admissible forms per field make value standardization harder.

example65,170,000,000 → 65170 (millions)

Knob 6 Normalization · Matching · Fusion

Value noise

Corrupts a share of values with typos, encoding artifacts, and truncation. The damaged values lower string-similarity scores during matching and show up as spurious disagreements during fusion.

example2005-01-01 → 2o0t-01-o1

Knob 7 Schema matching

Schema naming divergence

Renames source columns along a scale from fully descriptive, through abbreviated, to opaque codes. At the hard end the column name carries no signal, so a matcher has to rely on the values alone.

exampletotal_assets_val → ta

Knob 8 Fusion

Source reliability

Reshuffles which source holds the correct value per attribute, so the most reliable source is right for only a share of entities. No fixed source-trust rule stays optimal.

exampleAccor: the verified name is reassigned to a different source

Full specifications for every knob are in the repository. The knob cards there use an older numbering from 01 to 10: knobs 1 to 6 above are cards 01 to 06, knob 7 is card 08, and knob 8 is card 10. Cards 07 (value ambiguity) and 09 (schema completeness and distractors) are specified but not used in the released variants. The variant generator and the committees that measure the difficulty of the variants are in usecases_synthetic.

Conclusion

This paper introduced the Mannheim Data Integration Benchmark (MaDI-Bench). The benchmark covers all steps of the data integration process, from schema matching and value normalization through blocking and entity matching to data fusion, and evaluates each step as well as the integrated output, taking into account the dependencies between the steps. To prevent a quick saturation of the benchmark as agentic systems progress, we introduced a generic variant-generation method for deriving harder as well as easier variants from the base tasks. We validated MaDI-Bench and the generated variants using human-designed pipelines, an LLM workflow, a best-of-breed pipeline, and a Claude Code integration agent. The validation showed the benchmark's utility for measuring the step-wise as well as end-to-end performance of data integration pipelines. We hope that the benchmark will prove useful for the community and will support the development of fully automatic as well as human-in-the-loop data integration systems.

Downloads

Tasks are released as plain files (CSV, JSON, JSON Lines, and XML), so any system can read them. The evaluation package of the repository scores value normalization and data fusion; schema matching, blocking, entity matching, and the end-to-end metrics are scored with the evaluators of PyDI at the commit that the repository pins. The repository README describes the submission formats and the commands.

  • Benchmark repository: all 20 tasks with their ground truth, the evaluation code, the variant generator, the code of P1, P2, and P3, the skills and prompts of P4, and the outputs and scores of the validation runs.
  • PyDI: the integration framework and the per-step evaluator classes.
  • The tasks: source tables, target schemas and taxonomies, gold schema mappings, and the labeled entity matching, normalization, and fusion sets.
